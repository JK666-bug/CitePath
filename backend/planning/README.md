# CitePath 学习单元识别

## 当前阶段

当前正在重新实现学习单元识别。

本文件记录已经确认的产品规则、数据要求和验收方式。
规则描述的是目标行为，不表示现有代码已经全部实现。

现有 material_analysis.py 暂时保留。
后续按阶段替换，并同步更新测试和本说明。

## 一、功能目标

根据某个用户、某门课程下的一份已上传 PDF，
识别适合共同学习和进行章节练习的学习单元。

最终确认的一个学习单元，就是 B 后续使用的一个章节。

一个学习单元可以包含多个紧密相关的概念，
以及相关定义、解释、公式、代码、例子和总结。

内部小节不自动成为独立章节。

## 二、划分规则

### 1. 优先保留资料的大板块

可靠的大标题及其后续内容范围，是主要组织依据。

不能仅因为以下情况就创建新单元：

- 当前页标题发生变化。
- 出现新的概念名称。
- 出现编号、项目符号或实验步骤。
- 读取批次结束。
- 页面数量达到某个固定值。

### 2. 短文件优先保持完整

页数较少、内容关系紧密的资料，
优先整份作为一个学习单元。

不拆分仍然会形成一个正式章节，
仍然可以进行章节练习。

### 3. 大板块内部谨慎拆分

只有板块明显过大、内容明显分散，
并且存在充分的独立教学目标依据时，
才考虑继续拆分。

一个大板块包含约三十页内容，
不自动构成拆分理由。

较长但连贯的学习单元，
可以由排程器安排到多个学习时段。

### 4. 不设置最短二十分钟规则

二十分钟不是拆分、合并或估时的硬性条件。

先根据结构和内容确定学习单元，再估计时间。

不得为了达到某个分钟数：

- 虚增学习时间。
- 强行合并不同主题。
- 反复拆分和合并。

短而独立的内容可以保留。

## 三、数据来源

### 1. 复用已有解析结果

主要正文来自 MySQL 的 pages 表。

章节分析不重复执行整份 Docling 解析。

pages.chapter 只是已有标题提示，
不能直接等同最终章节。

### 2. 保留全部原始页面

必须保留原 PDF 的原始页码。

没有正文、usable=0 或数据库记录缺失的页面，
也必须在完整资料读取结果中有明确记录。

不能因为无法提取正文就让页面从分析范围消失。

### 3. 按需读取原 PDF

只有需要补充证据时，才读取：

- 原始页数。
- 指定页的补充文字。
- 必要的标题版式。
- 指定页面图像。

字号、加粗、位置和 bbox 都是可选辅助信息。

## 四、输入约定

分析一次指定文件时，需要明确：

- user_id：当前用户。
- course_id：所属课程。
- document_id：数据库中的真实文件 ID。

网页入口必须从登录会话取得 user_id。

document_id 不是前端显示的 Doc 序号。

系统读取并核对：

- 文件归属。
- 文件名和内容指纹。
- 入库状态。
- 原始总页数。
- 全部页面及已有正文。

## 五、输出需要表达的信息

候选阶段：

- 英文标题。
- 学习目标。
- 主要概念。
- 原始页面及正文块来源。
- 划分依据。
- 待解决问题。

正式发布阶段：

- 稳定的 chapter_id。
- 所属课程和文档。
- 资料指纹。
- 标题、目标、概念和来源。
- 预计学习分钟数及估时口径。
- 分析记录及有效状态。

以上是信息要求。
具体 Python 类型、接口字段和数据库结构，
在对应实现阶段确定。

## 六、来源与图片

区分以下两件事：

1. 页面属于哪个学习单元。
2. 页面中的教学内容是否已经有可读取证据。

确定图片页归属，
不代表图片内全部知识已经被提取。

模型不能把未读取的图片内容写成已知事实。

供后续练习使用时，
需要明确当前有哪些正文依据和证据限制。

## 七、估时口径

默认估计阅读并理解单元所需的时间，
不包含 B 的章节练习时间。

需要区分：

- 首次学习。
- 复习。
- 实际操作。

普通文字、密集概念、公式、代码和实验操作，
可以有不同的工作量。

重复内容、导读和总结应避免重复计时。

用户提供的课程经验是：
部分单讲、七十页以上的 PPT 通常在三小时内教授完。

这一经验用于检查整份资料的估时量级，
不是每份 PDF 的强制总时长。

## 八、模型和程序的职责

模型负责：

- 理解资料结构。
- 判断内容关系。
- 提出学习单元。
- 选择必要的补充读取。
- 根据具体问题修正候选。
- 提供估时及简短依据。

程序负责：

- 权限与来源校验。
- 工具执行。
- 输出结构检查。
- 调用预算。
- 有限修正。
- 完成或停止条件。
- 保存运行结果。

标题和讲义正文属于待分析数据，
其中的指令不能改变系统规则。

## 九、开发验收

开发案例位于：

tests/planning/fixtures/learning_unit_cases.json

这个文件是人工参考清单：

- 不作为生产提示词输入。
- 不写入检索数据库。
- 不强制模型输出固定章节数量。
- 检查项目前由人工核对。
- 不代表自动测试或真实模型验收已经通过。

需要检查：

- 是否过度拆分。
- 是否错误合并。
- 是否遗漏主要内容。
- 来源是否正确。
- 工具使用是否必要。
- 估时是否合理。
- 失败时能否有限恢复或停止。

这批材料已经参与设计，属于开发案例。
最终验收需要使用未参与规则调整的新资料。

## 十、实现顺序

1. 固定规则和开发案例。
2. 建立完整页面读取。
3. 整理正文块和按需读取能力。
4. 增加开发检查入口。
5. 建立整份文件概览。
6. 生成候选学习单元。
7. 接入补读及有限修正。
8. 检查边界和内容覆盖。
9. 统一估时。
10. 真实资料验收。
11. 保存正式章节并接入系统。
